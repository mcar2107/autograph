# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Autograph — генератор рукописного текста: пользователь вводит текст, выбирает рукописный шрифт и лист бумаги — из пресет-пака
или свою фотографию тетради, — сервис рисует страницы в браузере и отдаёт их в JPEG: одну страницу или всю пачку
архивом. Лист приходит фотографией, поэтому текстура, свет и микротени настоящие: чернила им подчиняются, а
геометрия текста выводится из найденной на снимке разлиновки — в том числе на листе, снятом лежащим на столе, где
линии сходятся к дальнему краю.

## Стек и сборка

React 19 + TypeScript (strict) + Vite 7, Tailwind 4, Radix-примитивы, zustand, react-router. Отрисовка страницы —
canvas; чтение контуров шрифтов — `opentype.js`, упаковка пачки — `jszip`. SPA: одна точка входа `index.html`.

Порог браузеров — `.browserslistrc` (`baseline widely available`, версии не фиксированы). `vite.config.ts` читает его
через `browserslist-to-esbuild`.

`npm run build:paper` и `npm run measure:sheet` собираются esbuild-ом в кэш и запускаются node-ом: декодирование jpeg
идёт в Chromium (в node декодера нет, а Playwright уже стоит для скриншотных тестов), сам анализ — чистый TypeScript
из `lib/paper`. Декодер и печать отчёта у них общие (`scripts/sheet-photo-report.ts`), поэтому замер одной

(`scripts/build-app-icons.ts`): растеризация svg в png — тоже Chromium, новых зависимостей ради иконок не появилось.

Сборка — ещё и PWA: `vite-plugin-pwa` кладёт в `dist` `manifest.webmanifest` и `sw.js`, а весь собранный проект —
в precache. Подробности — раздел «Офлайн и установка».

Деплой: GitHub Pages, `.github/workflows/deploy.yml` на push в `master`. Сайт живёт в подпапке `/<репозиторий>/`:
базовый путь приходит в сборку через `BASE_PATH` (без него — `/`, так работают dev, тесты и Storybook). Пути к файлам

кладёт его копию в `404.html`, иначе прямой заход на `/create-font` вернул бы 404.

Гейты отгрузки — `.github/workflows/ci.yml`: линтинг, проверка типов, `npm test` двумя шардами, `npm run test:pwa`
и `npm run test:stories` отдельными job; Chromium для stories кешируется по версии Playwright. Идут на каждый PR в `master`, и тот же workflow вызывает `deploy.yml` перед
сборкой: без зелёных проверок на Pages ничего не уходит. Скриншотные тесты в гейт не входят — эталоны живут только в
docker-образе Playwright.

## Как работает генератор

1. **Лист — фотография со своей разлиновкой.** `lib/paper/` описывает семью листов (вид разлиновки: клетка или
   линейка) и её экземпляры-фотографии. Разлиновка принадлежит **экземпляру**: контур листа в кадре, шаг, фаза
   первой линии, наклон в кадре, перспектива, изгиб линий, поля и линия поля со стороной — всё в
   пикселях его фотографии, рядом с полем освещения и картой текстуры. Общей меры у фотографий нет: сняты они с
   разного расстояния, а привести их к одному шагу можно только масштабированием, которое уводит текст с линий.
   Семья — группа, внутри которой рецепт раздаёт страницам фон. Число шагов на строку (в клетку пишут через одну)
   задаёт вид **листа** страницы, а не семьи: у своего листа — `kind` его записи (`PaperFamily.sheetKinds`), у
   пресета — вид семьи. Чистый лист лежит в семье клетки или линейки, но строка на нём — ровно заданный шаг; вид
   читают `getPageCalibration` (`model/geometrySelectors.ts`) и отпечаток кэша раскладки. Ненайденное поле —
   полтора шага от **стороны листа**, а не от края кадра, верхнее опускается до ближайшей линии
   (`lib/paper/sheetRuling.ts`).

   Контур (`SheetOutline`) — четыре угла листа в кадре, а не прямоугольник: лист снят под углом и лежит на столе,
   на обложке, рядом с соседним листом. `null` — лист во весь кадр, как у скана. Всё, что меряется по бумаге —
   разлиновка, поле освещения, карта текстуры, — смотрит только внутрь контура: стол вокруг листа темнее или
   светлее бумаги и увёл бы и уровень света, и порог линий. Меры идут в прямоугольнике, вписанном в контур
   (`lib/paper/resolveSheetBounds.ts`): у выпуклого контура с почти осевыми сторонами каждая сторона
   прямоугольника берётся по внутреннему из двух углов. Отступа внутрь сверх этого нет — первая линия у края
   прямоугольника легла бы в начало профиля, и верхнее поле ушло бы в фолбэк.

   Перспектива (`RulingPerspective`) — не преобразование кадра, а дробно-линейная координата вдоль линий
   (`lib/paper/rulingPerspective.ts`): `U(x, y)` одна у всех точек одной линии и равна `firstLinePhase + k·step` у
   линии `k`, а знаменатель `1 + q_x·(x − x₀) + q_y·(y − y₀)` сводит линии к краю кадра. При нулевых схождениях
   она вычисляется тем же выражением `y − x·tgθ`, что и координата прямой наклонной гребёнки, без единой лишней
   операции — ровный лист не меняется ни в одном числе. Поэтому шаг, фаза, поля и изгиб сохраняют прежний смысл, а
   лист на столе описывается одним добавленным полем `perspective` (`null` — линии идут через равный шаг): слои
   выше меняют `u = y − x·tgθ` на вызов `lineCoordinateAt`, а не заводят вторую геометрию. Обращение
   `lineHeightAt` делит на `1 − a·q`, и вдали от нуля этот знаменатель держит не оно, а измерение: годной
   считается только перспектива, у которой он не ближе половины к нулю во всех углах кадра.

   Изгиб (`RulingBend`) — вертикальные смещения линий поверх прямой наклонной гребёнки на равномерной сетке узлов:
   по `x` узлы стоят в центрах равных полос области с линиями, строки узлов — линии гребёнки по координате вдоль
   линий `u = y − x·tgθ`. Сетка несёт свою меру, поэтому выборке (`lib/paper/sampleRulingBend.ts`) не нужны ни
   ширина кадра, ни шаг. Между узлами по `x` — кубический Катмулл — Ром: гладкая производная нужна повороту букв
   без контура, и на узлах строка не ломается. Смещение положительно вниз, `null` — лист ровный. Поле в разлиновке
   обязательное: забытый перенос изгиба (сборка разлиновки, отражение) ловит компилятор.

   Боковые поля и линия поля — **отрезки по двум концам** (`lib/paper/sideEdges.ts`): `margins.left`,
   `margins.right` и `marginLineX` — концы у верха кадра, `sideSlant` — у низа (`null` — концы те же, что у верха).
   Концы отсчитаны в системе блока, повёрнутой на наклон разлиновки, — `x` вдоль строки на высоте блока `0` и на
   высоте кадра, — поэтому равные концы — ровно перпендикуляр к строкам, как у поля одним числом, и
   `normalizeSideSlant` сводит такие концы к `null`: у поля без наклона одна запись, и раскладка с отрисовкой идут
   прежним путём до бита. Лист на столе лежит в кадре трапецией, и поле вдоль его стороны наклонено; одно число
   давало бы вертикаль и пустой клин между краем листа и текстом. Концы у низа — отдельное поле, а не пара вместо
   числа: запись без него (профили пресетов, прежние свои листы) читается как раньше, `PAPER_PROFILES_VERSION` его
   не учитывает. Автомат наклона не ставит — поля и линия поля из детектора без наклона, наклоняют их в редакторе.
   Поле обязательное, как `bend`.

   Линия поля и боковые поля зеркальной страницы — отражение оригинала, если в редакторе они не заданы отдельно:
   тогда они лежат в `mirrorOverride` (`null` — отражение) вместе со своими концами у низа. Поле обязательное по
   той же причине, что и `bend`.
2. **Импорт фотографии.** Импорт своего листа, перемер и сборка пресет-пака идут одним путём —
   `lib/paper/measureSheetPhoto.ts`. В приложении он работает в воркере разбора (`model/measureSheet.worker.ts`,
   клиент — `model/createMeasureSheetClient.ts`, вход — `useSheetImport/analyzeSheetPhoto.ts`): воркер получает
   файл, сам декодирует его, считает каналы снимка, меряет и кодирует карту текстуры, а каналы `luminance` и
   `redMinusGreen` возвращает transferable-буферами — редактору они нужны для магнитов. Числа те же, что у
   `measureSheetPhoto` в основном потоке, до бита; без `Worker` (jsdom) тот же разбор идёт в основном потоке.
   Порт открывается на первое задание, упавший воркер отказывает ждущим, и следующее задание открывает новый.
   `build:paper` и `measure:sheet` меряют в node, без воркера.

   Сначала ищется контур (`lib/paper/detectSheetOutline.ts`): каждая сторона кадра режется на полосы, в каждой
   берётся перепад яркости между поверхностью и бумагой, по голосам полос
   проводится прямая, крайние полосы не голосуют — там скруглённые углы. Ненайденная сторона остаётся краем кадра:
   лист, снятый впритык, теряет не контур, а одну его сторону. Дальше всё меряется в вырезке — вписанном в контур
   прямоугольнике. Лист во весь кадр вырезки не делает и разбирается ровно как прежде, до бита: копия пикселей не
   бесплатна, а мерить в ней нечего.

   Шаг разлиновки ищется автокорреляцией профиля яркости по всему кадру с уточнением по спектру, угол —
   свипом ±2° по резкости горизонтальных линий со сверкой по вертикалям (`lib/paper/detectSkewAngle.ts`): если угол
   линий размывает вертикали (линию поля, концы линий, линии клетки) ниже половины их лучшей резкости, он уведён
   изгибом, и берётся угол вертикалей.

   Профиль по кадру — первая ступень шага: пока он берёт порог уверенности, полосы не считаются, и числа ровного листа
   не меняются до бита. У листа, снятого на столе, шаг по кадру плывёт, общий профиль размывается и порога не берёт —
   тогда вторая ступень (`lib/paper/measureBandedPeriod.ts`) режет кадр поперёк линий на полосы по семь шагов, и в
   каждой свой свип наклона и свой период. Шаги, кратные наименьшему, делятся на кратность: иначе выбор между шагом
   клетки и удвоенным решала бы разбивка кадра. Разлиновка найдена, если период есть хотя бы в двух соседних полосах,
   шаги полос ложатся на прямую `step(u)` с невязкой меньше 3 %, а гребёнка держится через каждую полосу и через
   70 % кадра: тень, текстура или блок текста в монотонный ряд по высоте не выстраиваются. Наружу уходят шаг в
   середине области с линиями, фаза и наклон ближайшей к ней полосы, а наклон `step(u)` засевает схождение по высоте
   в поиске перспективы. Уверенность остаётся от профиля по кадру, поэтому у листа, найденного полосами, она ниже
   порога.

   Поля ищутся по профилю в предсказанных положениях линий. Линия поля — тоже в две ступени: сначала по профилю
   столбцов во всю высоту, а не найдя там или не подтвердив найденное — полосовым опросом. Черта, идущая в кадре не вертикалью, в профиле во всю
   высоту тонет среди вертикалей клетки, поэтому область с линиями режется на полосы в полшага: в полосе в полтора
   шага черта размазывается по столбцам, и барьер не берётся. Кандидаты — пики в крайней трети ширины у самой
   глубокой полосы и двух соседних; каждый ведётся трассой по всем полосам и оценивается медианой глубины своих узлов
   при охвате не меньше пятой доли полос: среднее с нулями повторило бы размывание, а без охвата побеждал бы одиночный
   узел пересечения с вертикалью клетки. Пик ближе полшага к краю полосы кандидатом не становится — там обрыв
   «бумага → обложка» читается как провал. Барьер той же формы, что у профиля, — полтора квантиля 0,9 соседних
   вертикалей, 6σ или 0,03, — но соседи меряются той же трассой.

   Кандидат профиля во всю высоту сам линией не становится: его подтверждает **вето по стороне** — полосовой опрос
   его стороны той же мерой целиком, с трассами, медианой, охватом, правилом края полосы и барьером по соседям
   трассы. Подтверждается сторона, а не положение: `x` кандидата в опросе не участвует, на самом кандидате
   проверяются только правило края полосы и краснота. У черты, идущей не параллельно разлиновке, пик профиля — её
   среднее положение, и полосы находят её в трети шага и дальше от него (`IMG_1802`, `IMG_1804`: 0,27…0,41 шага),
   поэтому сверка положения отвергла бы годные линии. Цена — ложный кандидат у стороны с настоящей чертой вето по
   стороне проходит. На цветном снимке его снимает вето по цвету — краснота мерится по трассе от `x` кандидата, —
   на бесцветном его не держит ничто. Дециль соседей в профиле во всю высоту не локальна: на клетке со схождением вертикали совпадают со столбцом кадра
   лишь в узкой зоне, и граница крайней трети, разрезав её, пропускает через барьер обычную вертикаль клетки
   (`IMG_1813`: 1,26 барьера в профиле, 0,96 — полосовой мерой). Вето стоит до уточнения трассой и до обрезки сетки
   изгиба, на обоих проходах, и `x` не меняет: подтверждённая линия сохраняет положение первой ступени до бита.
   Отвергнутый кандидат линию не отдаёт, а передаёт поиск второй ступени у тех же краёв, что и профиль: на проходе
   по кадру — с обеих сторон, на выпрямленной копии — только у стороны, найденной ровным проходом. Та выбирает
   самого глубокого среди кандидатов, прошедших и барьер, и вето по цвету: сравнение глубин сторон до барьера
   теряло бы годную черту, когда у другой стороны кандидат глубже, но барьера не берёт.

   **Вето по цвету.** Яркостью черту поля от витка спирали, тени и вертикали клетки не отличить: такие фантомы
   проходят и барьер, и полосовую меру (`IMG_1705` справа — 3,19 и 2,91 барьера на кадре и копии, `IMG_1808` — 3,00
   и 3,01), а отстояние от фазы клетки, край вырезки и глубина у настоящих и ложных перекрываются. Различает
   краснота: черта поля красная, бумага и клетка — нет. У `SheetImageData` есть необязательный канал `redMinusGreen`
   (`R − G`, построчно, как яркость); его кладут `decodeSheetImage` (импорт и перемер своего листа) и
   `decodeSheetPhoto` (`build:paper`, `measure:sheet`), а вырезка и выпрямленная копия переносят его тем же
   отображением пикселей, что и яркость, — иначе на копии краснота бралась бы не из столбца кандидата. Краснота
   кандидата (`lib/paper/marginLineRedness.ts`) — медиана по узлам трассы избытка `R − G` над скользящей медианой
   строки, в узле — наибольший по бину кандидата и двум соседним; считается она лениво, только в бинах у узлов
   кандидата. Кандидат любой ступени с краснотой ниже `MARGIN_LINE_MIN_REDNESS = 16` уровней не принимается: на 34
   живых снимках настоящие дают не меньше 26,5, ложные — не больше 6,1. Краснота только отнимает кандидатов, а
   положение и порядок по глубине остаются от яркости, поэтому у настоящих линий и пресетов числа те же до бита.
   Поиск по профилю красноты вместо вето сдвинул бы `x` найденных линий — у `IMG_1812` на 27 px.

   **Гейт серого снимка.** Если P99 `|R − G|` по кадру ниже `MARGIN_LINE_COLOUR_GATE = 5` или канала нет, вето по
   цвету выключено, и поиск идёт только по яркости: на сером скане ни один кандидат красноты не набрал бы, и тёмная
   черта терялась бы. Мера берётся по полному кадру, один раз на оба прохода и лениво — когда кандидату впервые
   нужна краснота. Цветные снимки дают по кадру 17…59, серый скан — 0…1; по вырезке цветные опускаются до 5, и порог
   на ней лёг бы без запаса. Цена гейта — на бесцветном снимке яркостные фантомы выше барьера становятся линией: их
   держит только цвет.

   **Повторная трасса.** Трасса кандидата стартует с самого глубокого узла и отсекает узлы мельче 0,8 от старта. На
   перекрёстке черты с вертикалью сходящейся клетки глубины складываются (около 0,72 против 0,48…0,50 у самой
   черты), порог трассы встаёт выше глубины черты, и она обрывается, не взяв охвата, — вето по стороне отвергло бы
   настоящую черту. Поэтому кандидат без охвата 0,2 трассируется заново со старта строго мельче 0,8 от прежнего,
   пока охват не набран или потолок следующего старта (0,8 от прежнего) не опустился ниже `MARGIN_LINE_MIN_DEPTH`.
   Уже годных кандидатов, соседей и барьера повтор не касается, и калибровка барьера остаётся в силе. Порог трассы
   от квантиля стартовых узлов снял бы обрыв и без повтора, но сдвинул бы глубины соседей, а с ними и барьер.

   Найденная любой ступенью линия уточняется трассой и обрезает сетку изгиба. Всё найденное сохраняется в разлиновку
   листа. Сама фотография не выправляется: выпрямление размыло бы текстуру, ради которой снимок и берётся.
   Неудача автоопределения не отбрасывает фотографию: лист добавляется с нулевым шагом разлиновки (маркер
   «линии не найдены»), и редактор разметки сообщает об этом и ставит две булавки для ручного закрепления.

   Перспектива (`lib/paper/detectRulingPerspective.ts`) ищется по тем же прослеженным линиям в пяти вертикальных
   полосах области с линиями — между боковыми полями: за ними пружина, переплёт и стол, и трасса ведёт их как линии.
   По узлам подгоняются наклон, фаза, шаг и два коэффициента схождения; схождение по высоте подгонка начинает с
   засева полосовой ступени шага. Записывается перспектива, только если пройдёт все проверки сразу — найдено хотя бы
   шесть линий и 60 % узлов, шаг между крайними линиями изменился не больше чем на 35 % (тетрадь, снятая на столе,
   меняет его до четверти; сорванную трассу отсекает не дрейф, а остальные проверки), знаменатель `1 − a·q` в углах кадра не ближе половины к нулю, невязка узлов
   меньше пятой доли шага, а расхождение с прямой гребёнкой больше двадцатой: перспектива мельче хранения не
   окупает ни байта, ни пересчёта контуров. Невязка меряется **за вычетом** постоянной по столбцу составляющей:
   изгиб бумаги в полшага иначе уносил бы с собой и перспективу, хотя меряется он отдельно и поверх неё. До двух
   сотых узлов с наибольшей невязкой отбрасываются по одному — сорванная трасса у края листа одна закрывала бы
   перспективу всему снимку, а прогиб, которого модель не описывает, сидит сразу во многих узлах, и такая доля его
   невязку не снимет. Не прошло — перспективы нет, лист меряется прямой гребёнкой.

   Найденная перспектива включает **второй проход**: вырезка выпрямляется уточнённым наклоном, и шаг, фаза и поля
   берутся уже с копии, где строка пикселей совпала с координатой вдоль линий, а сама перспектива — из детектора с
   переводом начала в кадр. Копия живёт только внутри измерения, в разлиновку листа уходят пиксели кадра. Отказ
   второго прохода виден в диагностике и оставляет числа ровного прохода. Шаг второй проход меряет теми же двумя
   ступенями, но с заданным наклоном — свип полос взял бы компромиссный угол с пружиной и столом, — а линию поля ищет
   только у стороны, найденной ровным проходом, и новую не заводит. Верхнее поле переносится на перспективную
   гребёнку в середине области с линиями: к краю ровная и перспективная гребёнки расходятся до трети шага, и
   округление у края взяло бы соседнюю линию.

   Изгиб (`lib/paper/detectRulingBend.ts`) прослеживается по вертикальным полосам в два шага внутри области с
   линиями: каждая линия ищется с центра и ведётся к краям от предсказания по соседней полосе. Независимый поиск у
   прямой гребёнки к краю цеплял бы соседнюю линию. Одиночные выбросы — соринки, текст, клетки на линии поля —
   снимает медиана соседних линий в том же столбце. Медиана по соседним столбцам срезала бы гребень волны. Изгиб
   проходит **проверку надёжности** и не сохраняется, если найдено меньше 60 % узлов, фильтр заменил больше 20 %,
   где-то смещение дошло до полушага (трасса перескочила на соседнюю линию), соседние линии в узле расходятся
   больше чем на четверть шага или наибольший отход линий от прямой меньше двадцатой шага — в узлах и у краёв
   области, куда он продолжается параболой через три крайних узла строки на полполосы за крайний узел
   (`measureBendDeviation`). Такой лист остаётся ровным, строки на нём идут по прямой наклонной разлиновке,
   отдельного сообщения пользователю нет.

   Границы области с линиями ищутся **трассой вдоль самих линий** — общий модуль `lib/paper/traceRulingLines.ts`,
   тот же, что у перспективы. Трасса стартует у середины, идёт по соседним полосам от предсказания и ведёт местный
   шаг, обновляя его, только если промежуток отличается от прежнего не больше чем на шестую долю: перескочив на
   соседнюю линию, трасса ушла бы по чужому шагу. Окно поиска — треть шага, край области — «окно не помещается», а
   не последняя позиция прямой гребёнки. Окно вокруг прямой гребёнки на снимке с волной у верха листа
   промахивается мимо первых линий, и верхнее поле съезжает вниз на несколько шагов — на живой тетради это
   четырёхкратная ошибка, а не доли пикселя. Боковые границы — линия поля, крайние вертикали клетки и концы горизонтальных линий — прослеживаются так же.
   Итог — положение, ближайшее к области письма, и наружу от меры по среднему профилю он не выходит: изогнутая
   граница не пускает текст за себя, а найденное поле — без наклона к строкам; вдоль наклонной стороны листа его
   ставят в редакторе.

   Граница области, упёршаяся в край вырезки, полем становится не сама: измерение смотрит по полосам, есть ли
   провал на шаг дальше крайней линии — одинаково у верхней и у нижней границы, — и берёт поле, только если у
   большинства полос его нет. Иначе — фолбэк от
   стороны листа: линии продолжаются за вырезку, и первая найденная не первая на листе.
3. **Редактор разметки.** Автомат ошибается, поэтому после каждого импорта открывается полноэкранный редактор
   (`ui/Generator/SettingsPane/SheetMarkupEditor/`); с плитки своего листа его открывает «Настроить», недоступная,
   пока идёт разбор. Экземпляр один: оба пути идут через стор редактора (`model/useMarkupEditorStore.ts`,
   `openSheetEditor`). Правки копятся в черновике и ложатся на лист только по «Сохранить»; закрытие с правками
   спрашивает подтверждение. Подвал панели — отмена и повтор кнопками, «Сбросить к найденному», «Отмена»,
   «Сохранить» — лежит вне её прокрутки: высота панели зависит от инструмента, и в прокрутке «Сохранить» уходило
   бы под край окна. «Удалить лист» — в конце прокрутки, разрушительной кнопкой: удаление не отменяется. Подзаголовок
   называет разметку сохранённой, если разлиновка или вид листа отличаются от найденных автоматом, — по значению, а
   не по ссылке: перечитанный из хранилища лист держит их разными объектами.

   Фотография лежит в окне с зумом и панорамой (перетаскивание, колесо, пробел; приближение — Ctrl/⌘ + колесо,
   подсказка — под окном), разметка — SVG-оверлей в пикселях фото. Окно обрезает сцену `overflow: clip`, а не
   `hidden`: по `hidden` оно остаётся прокручиваемым, и табуляция к ручке за краем прокручивала бы его в обход
   матрицы, а приближение колесом уезжало бы от курсора на величину прокрутки. Ручку, получившую фокус за краем,
   показывает `useRevealFocus`: сдвигает матрицу так, что ручка встаёт в середину окна по той оси, где не
   помещалась, синхронно, до прокрутки к фокусу браузером. Ручку, взятую указателем, фотография не догоняет. Линии оверлей рисует только через
   `getPageRuling`, `lineHeightAt` и `sampleRulingBend`, своей формулы нет: то, что видно в редакторе, — ровно
   строки страницы. Слои (контур, линии, поля, линия поля, булавки)
   прячутся флажками, вся разметка разом — пока зажата H (`MarkupLayers/useHideMarkupKey.ts`, по `code`, чтобы
   работала и в русской раскладке; в поле ввода и с Ctrl/Cmd/Alt — нет, потеря фокуса окном возвращает разметку).
   Скрытая разметка прозрачна и не ловит указатель, но остаётся в документе: ручка в фокусе фокус не теряет.
   Штрих разметки двойной (`MarkupStroke`): краска слоя на белой подложке с непрозрачностью 0,4. Непрозрачная
   подложка закрывала линию снимка, и совпадение с ней было не проверить; при 0,4 под подложкой остаётся 60 %
   перепада «линия — бумага» в sRGB, а краска к подложке над самой тёмной бумагой живых снимков (яркость 0,17)
   держит не меньше 3,9:1. Каналы снимка для магнитов приходят от импорта, а при открытии с плитки — заданием
   декодирования в воркер разбора; до их прихода правка идёт без магнитов, при закрытии они отпускаются.

   - **Вид разлиновки** — «Клетка / Линейка / Без разлиновки». «Без разлиновки» линий не ищет, магнит выключен,
     строки идут через заданный шаг; возврат к виду с линиями ищет их заново одним шагом истории.
   - **Контур** — четыре угла. Вывернутый контур и контур меньше четверти кадра по ширине или высоте не
     применяются. Годный контур перемеряет лист в воркере (`OutlineTool/remeasureOutline.ts`): свет, текстура и
     разметка автомата — заново, вид и `mirrorOverride` остаются; побеждает последний запрос, «Сохранить» на
     время перемера недоступно. У чистого листа линии не ищутся — поля подтягиваются внутрь нового контура
     (`rebuildBlankRuling`).
   - **Линии — булавки.** Булавка (`RulingPin`) — закреплённая линия с номером и двумя концами в пикселях фото.
     Гребёнку через булавки подгоняет `lib/paper/fitRulingPins.ts`: две задают её точно (непараллельные — схождение
     по ширине), три и больше — ещё и изменение шага по высоте, то есть перспективу листа на столе; линии
     гребёнки прямые. Изгиб подгонка снимает — его сетка отсчитана от прежней гребёнки, — а затем он заново
     прослеживается по фото и доводится до концов булавок (`refitBendToPins`: `refitRulingBend` и несколько
     проходов `editRulingBend` у концов): прослеженный изгиб ведёт линию по снимку, и без доводки нарисованные
     линии уходили бы с булавок. Расстановка, которая гребёнку не задаёт, разлиновку не меняет: булавки встают, где
     отпущены, последняя подсвечивается. Смена наклона при подгонке не сдвигает на фото боковые поля, линию поля и
     поля зеркала: их концы отсчитаны в системе блока, повёрнутой на наклон вокруг левого верхнего угла кадра, и те
     же числа при новом наклоне уехали бы к низу кадра на высоту, умноженную на изменение угла. Поэтому
     `reanchorSideEdges` (`lib/paper/sideEdges.ts`) переписывает концы под новый наклон через две точки границы на
     фото, поля зеркала — в отражённом кадре с обратным наклоном; поле без наклона к прежним строкам к новым
     наклонено. Верхнее и нижнее поля — высоты у левого края кадра — не пересчитываются, а без смены наклона
     разлиновка та же до бита. Поля зеркала так же переписываются при перемере контура и поиске линий по виду:
     автомат перемеряет поля страницы, но не зеркала. У каждой булавки показана невязка, между соседними — число
     шагов с ±; «Закрепить ещё линию», «Открепить». Начальные булавки (`deriveRulingPins`) — крайние линии области с линиями,
     плюс средняя при перспективе, концы на десятой доле ширины блока внутрь: у самого края блока магнит чаще
     не находит линию. Магнит (`snapToRulingLine`) ставит отпущенный конец на самую тёмную линию своего столбца в
     пределах трети шага; с Alt/Option — нет.
   - **Изгиб** — точку линии тянут поперёк линий (`editRulingBend`): ближайшая линия проходит через отпущенную
     точку, сдвиг гаснет к двум радиусам, а сетка узлов при нужде дорастает копиями крайних строк и столбцов.
     Рамка у курсора — фактический охват правки (`resolveBendReach`) с запасом на хвост Катмулла — Рома, поэтому
     линии за ней не сдвигаются. Радиус — слайдером, Shift — весь столбец. «Подогнать по фото» — тот же
     `refitBendToPins`; ничего не найдено — ручной изгиб остаётся, и об этом сообщение. «Выпрямить» — строго
     прямые линии, невязка булавок показывается. Линия, которую возьмёт нажатие, подсвечена под курсором — та же
     ближайшая в столбце, что берёт `findLinePoint`, а не верхняя из перекрытых полос захвата: на мелком масштабе
     полоса в 14 экранных пикселей накрывает соседние линии. За одно перетаскивание линия уходит не дальше шага
     разлиновки у взятой точки, дальше сдвиг останавливается: за шагом она легла бы на соседнюю линию снимка, а
     детектор уже полшага считает перескоком трассы. Ограничение от масштаба не зависит — при обычном приближении
     его не достать, а на мелком рывок мыши в десятки экранных пикселей гнул бы линию на несколько шагов.
   - **Поля** — область текста правится **четырьмя углами**, как контур листа (`MarginsTool/marginsGeometry.ts`,
     `placeMarginCorner`): угол — пересечение верхней или нижней направляющей с боковым полем, и тянут его в обе
     стороны сразу. По высоте угол ведёт направляющую целиком — отпущенная встаёт на ближайшую линию, соседний угол
     едет по высоте вместе с ним; вдоль строки — только конец своего бокового поля, и поле поворачивается вокруг
     другого своего угла. Сначала ставится направляющая, потом столбец на ней: иначе конец поля встал бы в строке
     до прилипания к линии, и угол ушёл бы с указателя вдоль наклонного поля. Сдвиг угла — один шаг истории.
     Стрелки у угла — по одной оси (`resolveCornerMove`): ←→ — конец поля, ↑↓ — поле по высоте на пиксель мимо
     линий. Ручка в середине верхнего и нижнего края осталась и двигает только поле по высоте: угол всегда тянет и
     боковое поле, и сдвинуть рукой одну верхнюю строку, не задев полей по бокам, иначе не выйти. Линия поля
     правится **двумя ручками** на трети и двух третях высоты листа и идёт через обе. Угол и ручка ограничиваются
     в своей строке (левое поле не правее правого, линия поля внутри листа), а не концы у верха и низа кадра:
     ограничение концов повернуло бы границу мимо ручки. Оверлей рисует боковые
     границы теми же точками (`sideEdgePointAt`), по которым раскладка ставит начало строк. Линию поля можно убрать
     и добавить: новая появляется у ближайшей стороны без наклона и сразу тянется. **Цветовой магнит линии поля**
     (`lib/paper/snapMarginLine.ts`) ищет в окне трети шага избыток `R − G` над скользящей медианой строки — той же
     меры, что вето по цвету в детекторе, — с порогом `MARGIN_LINE_MIN_REDNESS`: по яркости красная черта
     бледнее вертикалей клетки, и самая тёмная вертикаль окна чаще оказалась бы клеткой. Цветной снимок без черты
     в окне не притягивает никуда. Гейт серого снимка тот же, что у детектора: на сером снимке или без канала
     `R − G` магнит яркостный (`snapToMarginLine`).
   - **Точность** — лупа над указателем при перетаскивании (перекрестие — светлая линия с тёмной каймой и зазором
     в центре: одноцветное тонуло в линии своего цвета, а сходящееся в точку закрывало пиксель под ручкой),
     стрелки сдвигают ручку в фокусе на 1 px фото, с Shift на 10, без магнита; Tab ходит по ручкам, у каждой свой `aria-label`. «Точные значения» — шаг, фаза и поля
     числами; у бокового поля — по числу на угол, у линии поля — на ручку: столбец угла или ручки, у правого поля
     — отступ от правого края, и число ставит угол вдоль его направляющей туда же, куда его перетащили бы. Булавки встают на набранную гребёнку, и изгиб доводится до них без повторной подгонки, иначе
     набранная фаза уходила бы.
   - **Пробный текст** — страница по черновой разметке: текст из поля ввода (пустое — образец), а за ним до конца
     страницы — он же, повторённый одним абзацем: проверяется разметка всего листа, и у короткого текста низ
     страницы остался бы непроверенным. Шрифт, чернила и реализм — те же, что у прогона, а рисует страницу воркер
     отрисовки тем же путём, что JPEG (`TrialText/buildTrialTask.ts`). Заказ уходит через 150 мс после шага истории, а не во время перетаскивания;
     новая правка отменяет прежний заказ, опоздавший ответ не показывается. Воркер отдаёт страницу **целиком** —
     фотографию с чернилами, а не отдельный слой чернил: она ложится над снимком и под разметкой, и видимый
     результат тот же. Пока пробный текст включён, линии разметки приглушены до четверти, а у булавок остаются
     только концы: синие чернила лежат ровно на линиях, и линия в полную силу закрывала бы, сели ли на них буквы.
   - **Зеркальная страница** — вкладка «Страница / Зеркальная страница»: фотография и слой ручек отражаются
     матрицей, а данные — нет; правка на зеркале уходит в лист через `x → W − x`. Контур, линии, изгиб, верхнее и
     нижнее поля у страниц общие; линия поля и боковые поля зеркала — «Как у оригинала, отражённо» или «Задать
     отдельно» (`mirrorOverride`, поле не меньше 1 px) — теми же углами, ручками линии поля и числами, что у листа.
     Углы на зеркале — видимые углы его области текста (`placeMirrorCorner`): по высоте они правят общие поля,
     вдоль строки — поля зеркала; пока те отражены, угол ходит только по высоте, иначе дрожь указателя молча
     заводила бы отдельные поля зеркала.

   Черновик и его история — отдельный стор редактора: `commit(update, {coalesceKey})`, промежуточные значения
   перетаскивания — `preview` без шага истории. Ctrl/⌘+Z и повтор, пока редактор открыт, достаются его истории, а
   не документу генератора (`resolveHistoryTarget` в `useHistoryHotkeys`): свои листы в историю генератора не
   входят. «Сбросить к найденному» возвращает разлиновку и вид автомата (`measuredRuling`, `measuredKind`) с
   булавками, выведенными заново. «Сохранить» — одно действие стора `saveSheetMarkup`: разлиновка, булавки и
   вид; разметка автомата меняется только вместе с перемером контура. Лист, вид которого сменился, переезжает в
   семью этого вида, и выбор, стоявший на нём, едет с ним без шага истории.
4. **Стор.** `model/useGeneratorStore.ts` — единственный источник правды, один zustand-стор из трёх частей
   (`model/useGeneratorStore.types.ts`). Один, а не три: селекторы параметров страницы читают части сразу, а
   `useShallow` через два стора не работает.

   - **Документ** — то, что сохраняется и попадает в историю: текст, встроенный шрифт, чернила
     (`ink`: `auto`, `tone` из палитры по `toneId` или `custom` со своим цветом), семья, экземпляр листа и его
     закрепление, реализм (ступень `level` из `config/realismLevels.ts` или `custom`, флаги искажений, частоты,
     вариативность контуров), поправка геометрии, запас снизу, параметры сцены без изображения, `runSeed`.
   - **Просмотр** — `pageIndex`, `isSpread`, `zoom` (`'fit'` или доля пикселей кадра).
   - **Ресурсы** — пресет-семьи, свои листы, свой шрифт, своё изображение сцены, скрытый фон; при своих листах —
     `hasRestoredUserSheets` (чтение хранилища кончилось) и `unsavedUserSheetIds` (листы, которые хранилище не
     приняло).

   Уровень реализма хранится явно, а не выводится сравнением с таблицей: ручной набор, совпавший со ступенью, и
   правка таблицы меняли бы подпись у сохранённых сессий. Выбор ступени пишет её значения, правка любого поля
   реализма ставит `custom`. Цвет чернил и параметры почерка отрисовка берёт только из рецепта
   (`recipe.inkColor`, `recipe.handwriting`), а не из документа напрямую; «Перегенерировать» — `startNewRun`, новый
   `runSeed`. Компоненты подписываются селекторами, на несколько полей сразу — через `useShallow`.

   **История правок** (`model/useGeneratorStore.history.ts`) — `past` и `future` из снимков документа, глубина
   100 шагов, без зависимостей. Правки документа идут через `commit(patch, {coalesceKey})`: набор текста склеивается
   в один шаг в окне 800 мс, слайдер во время перетаскивания пишет значение без шага истории, а шаг ставит на
   `onValueCommit`. Просмотр и ресурсы в историю не попадают. Ctrl/⌘+Z, Ctrl/⌘+Shift+Z и Ctrl+Y перехватываются и в
   поле текста: оно контролируемое, и браузерный undo после программной установки значения непредсказуем. Пока
   открыт редактор разметки, те же клавиши достаются истории его черновика.

   **Сессия** — `persist` из `zustand/middleware` под ключом `autograph.session`, `version: 1`: документ плюс
   `isSpread`. Запись дросселируется на 500 мс (`model/sessionStorage.ts`), иначе набор текста писал бы
   `localStorage` на каждый символ; переполнение и запрет хранилища молча выключают сохранение. Чтение проверяет
   каждое поле отдельно (`model/sessionSchema.ts`) и подставляет дефолт только в негодное, а не отбрасывает сессию.
   Ссылки на листы проверяются позже, в `restoreUserSheets` и `setPresetFamilies`: в момент чтения сессии свои
   листы и профили ещё не загружены. Пропавший закреплённый лист снимает закрепление, неизвестная семья меняется на
   первую. Той же проверкой проходит шаг истории, снимок которого ссылается на удалённый свой лист. Свои листы
   читаются асинхронно, и до конца чтения (`hasRestoredUserSheets`) лист, которого ещё нет в списке, пропавшим не
   считается; страница, закреплённая на таком листе, показывает ожидание (`selectIsAwaitingUserSheets`), а не
   подставленную бумагу. Отказ чтения — пустой список.
5. **Автокалибровка.** `lib/calibrate/deriveGeometry.ts` выводит кегль, межстрочный интервал, верхний и левый
   отступы и ширину блока из разлиновки листа страницы и метрик шрифта (`lib/measure/measureFontMetrics.ts`):
   базовая линия первой строки садится на первую линию не выше верхнего поля, края блока — поля, сужённые линией
   поля. При наклонных полях или линии поля (`sideSlant`) у каждой строки свои края (`lineBounds`: сдвиг начала
   от `leftPadding` и ширина): строка начинается и кончается там, где её базовая линия пересекает наклонную
   границу, с перспективой (`resolveSideEdgeAt`). Края считаются на каждую базовую линию до низа кадра; строкам
   дальше массива достаются края последней. Без наклона `lineBounds` нет вовсе. Первая линия и высота под текст считаются в **координате вдоль линий** (`lineCoordinateAt`), а не в
   пикселях по высоте: на листе с перспективой шаг по кадру плывёт, и нижнее поле, отмеренное пикселями, отрезало
   бы слева и справа разное число строк. Без перспективы `U(0, y) = y`, и числа прежние. Геометрия считается на
   каждую страницу — у каждой свой лист. Слайдеры геометрии остались, но задают
   **поправку** поверх вычисленного, как и запас снизу, в долях шага разлиновки: так она одинаково сдвигает текст
   на листах с разным шагом. Модель строчного бокса одна на все слои:
   `lineStep = fontSizePx * lineHeight + lineSpacing`, базовая линия строки n — `topOffset + fontAscent *
   fontSizePx + n * lineStep`, где `lineHeight` и `fontAscent` берутся из `fontBoundingBox`. Разойдись эти формулы
   между расчётом и отрисовкой — строки уползают с разлиновки на треть шага за строку. Высоты модели — координата
   вдоль линий, а блок отрисовка поворачивает на наклон листа, и в повёрнутой системе блока та же высота короче в
   `cos θ` раз: рендерер умножает на него верхний отступ и базовые линии, но не кегль и не длины вдоль строки.
   Без множителя строка уходила бы с линии на `(1/cos θ − 1)·U` — у листа с наклоном в три градуса до пяти
   пикселей к низу кадра; без наклона множитель — ровно единица.
6. **Измерение и разбивка.** Ядро не трогает DOM само: `lib/measure/` описывает интерфейс `TextMeasurer` и его
   реализацию на скрытом offscreen-контейнере; ширины он отдаёт в долях кегля, в пиксели их переводит кегль
   страницы. `lib/paginate/` набирает страницы последовательно: каждая раскладывается под разлиновку своего листа
   (`lib/split/` режет текст на строки по ширине её блока за вычетом процента запаса: Linux Chromium раскладывает
   строку целыми пикселями, до 0,9 % шире замера). На листе с наклонными полями ширина у каждой строки своя
   (`lineWidths` по номеру строки на странице), и нижние строки у расходящихся к низу полей вмещают больше слов. Строка ставится, пока её базовая линия не ниже нижнего поля
   листа, — хвосты букв последней строки могут зайти в поле. Результат кэшируется в `model/measureLayout.ts`:
   параметры, не меняющие переносы, применяются без повторного измерения. Концы полей у низа кадра входят в
   отпечаток листа: они меняют ширину строк.
7. **Рецепт прогона.** `lib/recipe/` выводит из одного seed всё случайное: экземпляр листа на каждую страницу,
   цвет чернил из палитры правдоподобных, параметры неровности почерка, параметры вариативности контуров, оптику
   (качество JPEG). Постраничные величины берутся из независимых подпотоков `seed ^ hash(pageIndex)`, поэтому
   дописанный абзац не перекрашивает чернила и не меняет уже показанные листы. Правка текста рецепт сохраняет,
   смена — только по явному действию.
8. **Отрисовка.** `lib/render/` рисует страницу на canvas: страница равна кадру своего листа, фотография ложится
   на неё целиком, без масштаба и сдвига, чернила — на прозрачный слой. Буквы ставятся контурами глифов
   (`lib/glyph/`), у каждого вхождения свой шум: точки смещаются, но границы стыка с соседней буквой заморожены,
   иначе рвутся соединения связного почерка. Слой чернил прогоняется шейдером `lib/ink/`, который умножает их на
   поле освещения и карту текстуры листа; у листа с непригодным полем (равномерный скан) берётся синтетический
   свет. Чётные страницы — правая половина разворота: фотография и поле освещения отражаются вместе с разлиновкой
   (`lib/paper/mirrorSheetRuling.ts`: линия поля и поля меняют сторону, наклон — знак, фаза сдвигается на наклон
   во всю ширину кадра; у изгиба столбцы узлов идут в обратном порядке, сетка ложится зеркально, а начало строк
   узлов сдвигается на тот же наклон, что и фаза; у перспективы начало переезжает в `W − x₀`, а схождение по
   ширине меняет знак — схождение по высоте и `y₀` отражение не трогает; у контура углы переезжают по горизонтали
   и левые меняются местами с правыми, иначе обход четырёхугольника вывернулся бы и вписанный прямоугольник вышел
   бы за лист; у концов полей у низа кадра левое и правое меняются местами, линия поля переезжает в `W − x`). Линия
   поля и боковые поля, заданные для зеркала отдельно (`mirrorOverride`), встают вместо
   отражённых, а у отражённой разлиновки замена обнулена. Отражённую разлиновку берут и раскладка, и отрисовка —
   один селектор в `model/geometrySelectors.ts`, его же берёт оверлей редактора на зеркальной странице. Изгиб,
   перспективу, контур и замену зеркала применяет только `mirrorSheetRuling`: параметры страницы берут готовые
   поля из разлиновки страницы.

   **Изгиб и перспектива в отрисовке** — один механизм: точка строки ставится не на `y`, а на `Y(x, U) + d` —
   высоту своей линии в её столбце плюс смещение изгиба. Включается он только при непустом `bend` или
   `perspective`; на ровном листе без перспективы ни выборка, ни перевод координат не вызываются, и лента вызовов
   контекста та же, что у листа без изгиба и перспективы. Рядом со стеком канвы рендерер ведёт ту же матрицу без масштаба и сдвигает каждую
   точку контура, контрольные точки кривых тоже, на разницу между местом линии и `y` в её точке страницы,
   переведённую обратной линейной частью в локальные координаты буквы. Стык соседних букв — одна точка страницы с
   одним сдвигом, поэтому соединения связного почерка не рвутся. Неровность почерка и поправка геометрии уже вошли
   в матрицу, и линия ложится поверх них. Сдвиг точками, а не деформацией готового слоя чернил в шейдере: без WebGL
   он пропал бы вместе с модуляцией, а ленту вызовов тесты попадания уже не видели бы.

   **Побуквенный путь** достаётся буквам без контура: своему шрифту и встроенному, пока его `.ttf` не разобран. На
   изогнутом листе и на листе с перспективой слово рисуется по одной букве. Каждая сдвигается на смещение в
   середине буквы на базовой линии и поворачивается на `atan(tgθ + ∂d/∂x) − θ` — по касательной к своей линии за
   вычетом наклона, уже учтённого матрицей. Целое слово с одним сдвигом осталось бы прямым и в углу листа ушло бы с
   линии больше чем на десятую шага.

   **Раскладка от изгиба не зависит, от перспективы зависит.** Кегль, интервал, отступы, вместимость и переносы
   считаются по гребёнке без изгиба: `lib/calibrate`, `lib/paginate` и отпечаток кэша `model/measureLayout.ts`
   поле `bend` не читают — изгиб сдвигает уже разложенные строки только при отрисовке. Иначе переимпорт листа с
   чуть другим изгибом менял бы число строк на странице. Цена — базовая линия последней строки может уйти ниже
   нижнего поля на величину изгиба, меньше полушага. Перспектива, наоборот, входит и в геометрию, и в отпечаток
   кэша: она меняет сам шаг по кадру, а с ним число строк, и раскладка по прямой гребёнке уводила бы низ страницы
   с линий на целую строку — это не поправка поверх готовой раскладки.

   **Наклонные поля в отрисовке** — те же края строк, что у разбивки (`RenderGeometry.lineBounds`): строка
   сдвигается вдоль себя на свой сдвиг и не пускает слова за свою ширину, вокруг её середины она и качается.
   Сдвиг отсчитан в системе блока так, что после поворота на наклон начало строки встаёт в столбец пересечения
   границы с её линией, а перспектива и изгиб двигают точку только по высоте — и приводят её ровно в это
   пересечение. Без `lineBounds` сдвиг нулевой, и лента вызовов та же, что у поля одним числом.
9. **Экспорт.** Предпросмотр и снимок идут **одним** путём и отличаются только масштабом. Отрисовка страниц уехала
   в Web Worker на `OffscreenCanvas`, поэтому интерфейс не замирает; через границу воркера идут только числа и
   строки, фотография передаётся `ImageBitmap`, шрифт и карта текстуры разбираются на его стороне. Тем же воркером
   рисуется пробная страница редактора разметки. Разбор фотографии листа — отдельный воркер (п. 2). Растр —
   JPEG в разрешении кадра листа: фотография бумаги не бывает PNG. Пачка (`lib/batch/`) обрабатывает страницы по
   одной — страница кодируется и освобождается до отрисовки следующей, размер у каждой свой, — упаковывает их в
   архив с сортируемыми именами, показывает прогресс и умеет отмену; ошибка отдельной страницы не теряет
   остальные. Вложение страницы в сцену (`lib/export/`) осталось необязательным шагом: фотография листа часто уже
   снята на столе.

В снимок попадает только страница — панель настроек и навигация лежат вне пути отрисовки.

## Ассеты

- Шрифты — `public/fonts/*.ttf`, объявления `@font-face` — в `src/app/styles/app.css`, список для панели —
  в `pages/Generator/config/fonts.ts`. Добавляя шрифт, правь оба места. Отрисовка читает тот же `.ttf` напрямую,
  чтобы получить контуры глифов.
- Пресет-пак листов — `public/paper/{grid,lined}/*.jpg` плюс карты текстуры `*.texture.png` рядом и артефакт
  `public/paper/profiles.json` с разлиновкой каждого экземпляра (контур, шаг, фаза, наклон, перспектива, изгиб,
  поля, линия поля). Артефакт пересчитывается `npm run build:paper` и коммитится: в рантайме фотографии не
  разбираются. Скрипт печатает по каждому листу контур по сторонам и углам, полосовую ступень шага (не
  понадобилась, не сошлась или шаги полос с дрейфом), перспективу (шаг у крайних линий, дрейф, расхождение гребёнок,
  причину отказа), линию поля со ступенью, которой она найдена (у полосового опроса — охват полос, отношение глубины
  к соседям и связавший порог: `соседи`, `сигма` или `минимум`; калибровать множитель соседей там, где кандидата
  держал сигма-этаж, — крутить не то число), вердикт первой ступени по кадру и, если был второй проход, по копии
  (принят, отвергнут стороной или цветом, вето не звалось — с охватом, отношением, барьером и краснотой) и гейт
  серого снимка: включено ли вето по цвету и P99 `|R − G|` кадра, `канала нет` или `цвет не понадобился`, если до
  красноты не дошёл ни один кандидат. Печатает он и наибольший отход изгиба в долях шага — тот же, по которому
  решает проверка надёжности, с краями области, — и долю найденных узлов: по ним сверяются пороги проверки надёжности.
  Пресеты сняты вплотную к листу и без завала, поэтому у всех восьми и `outline`, и `perspective` — `null`; сам
  путь измерения от этого не отличается.

  `npm run measure:sheet -- <фото> [grid|lined|blank]` печатает те же строки по одной фотографии, не трогая
  артефакт: так принимается разбор снимка, которого в пресет-паке нет. Вид просят явно, потому что `blank`
  отключает поиск разлиновки, а клетку от линейки измерение и так различает по снимку.

  Изгиб, контур, перспектива, замена полей зеркала и концы полей у низа кадра в артефакте и в записи своего листа
  — необязательные поля `bend`, `outline`, `perspective`, `mirrorOverride`, `sideSlant`; смещения изгиба округлены до сотых пикселя ещё при измерении.
  Отсутствующее или испорченное поле читается как «ровный лист», «лист во весь кадр», «линии через равный шаг»,
  «зеркало — отражение», «поля без наклона» (`model/paperSheetJson.ts`), а не как сломанная запись: сетка изгиба не по длине
  `offsets`, контур хоть с одним негодным углом, перспектива, у которой в углу кадра знаменатель `w` или `1 − a·q`
  не больше нуля (одного `1 − a·q` мало: за горизонтом он и числитель меняют знак вместе), замена зеркала или
  концы у низа с негодным боковым полем — всё это `null`, а не отброшенный лист. Поэтому `PAPER_PROFILES_VERSION` эти поля не
  учитывает: поднятая версия заставила бы приложение отбросить весь артефакт. Свой лист без них в записи остаётся
  ровным листом во весь кадр до переимпорта или правки в редакторе: при запуске фотографии не разбираются. Карта
  текстуры лежит отдельным файлом, а не строкой в артефакте: в base64 это около мегабайта на снимок, а файл ещё и
  кэшируется браузером.
- Семьи листов — `pages/Generator/config/paperFamilies.ts`: вид разлиновки и экземпляры. Без артефакта семьи всё
  равно доступны, но разлиновка экземпляров синтезирована: шаг — доля кадра, поля — фолбэком, фаза нулевая.
- Сцены — `public/bg7.jpg`, `public/bg10.jpg`.
- Иконки приложения — `public/icon-192.png`, `public/icon-512.png` и `public/icon-maskable-512.png`: их перечисляет
  манифест в `vite.config.ts`. Рисуются не руками, а `npm run build:icons` из того же `public/favicon.svg`, что и
  фавиконки, и коммитятся: в сборке Chromium не запускается. У `maskable`-варианта рисунок ужат в центральные 80 %
  холста, а фон растянут на весь квадрат — маска Android срезает углы, и скруглённый прямоугольник исходника после
  среза выглядел бы обкусанным. Фон берётся из `fill` первого `<rect>` фавиконки, жёсткая константа — только фолбэк.
  Правка логотипа — правка `favicon.svg` и прогон скрипта; на чистом дереве он файлы не меняет.
- Пользовательский шрифт подключается через FontFace API под именем `UserFont`.
- Свои листы живут в IndexedDB без зависимостей (`model/indexedDb.ts`, `model/userSheetsStorage.ts`): база
  `autograph`, хранилище `sheets`, ключ `id`. Запись (`StoredUserSheet`) — исходный файл фотографии `Blob`-ом без
  перекодирования, свет, карта текстуры `Blob`-ом с размером и размахом и разметка: `kind`, `ruling` с правками,
  `measuredRuling` и `measuredKind` автомата — к ним возвращает «Сбросить к найденному» и после перезапуска, —
  `pins`. Строковое хранилище с data URL-ами не годится: фотография в base64 весит на треть больше, а квота
  `localStorage` — единицы мегабайт на сайт, меньше пары снимков с телефона. Операции идут очередью транзакций;
  прочитанные фотография и текстура отдаются object URL-ами, которые освобождаются при удалении листа. Прочитанный
  лист считается разобранным.

  Запись асинхронная, `writeUserSheet` отвечает `false`, если хранилища нет, оно переполнено или файл не
  прочитался; лист в памяти правку получает в любом случае, а в стор попадает в `unsavedUserSheetIds`, и
  пользователь видит, что после перезагрузки листа не будет. Первая запись за сессию просит
  `navigator.storage.persist()`, чтобы браузер не вытеснял данные сайта.

  **Перенос из `localStorage`.** Листы прежних версий лежали в `localStorage`; при чтении они переносятся одной
  транзакцией (`model/userSheetsStorageMigration.ts`, прежний формат читает только
  `model/userSheetsStorageLegacy.ts`): data URL-ы становятся файлами, `kind` берётся из прежнего `isBlank`
  (`blank`) или из вида семьи, булавки выводятся из разлиновки. Прежние ключи удаляются после фиксации транзакции:
  сбой оставляет их, листы видны до конца сессии, и следующий запуск повторяет перенос. Запись с уже
  существующим `id` перенос не перезаписывает — она новее. Без IndexedDB (запрет данных сайта) читается только
  прежнее хранилище.

  Вид разлиновки (`kind`) лежит у листа, а не выводится из семьи: чистый лист (`blank`) живёт в семье клетки или
  линейки, а лист, вид которого поправлен в редакторе, переезжает в семью своего вида. Вид нового листа
  предлагает снимок, а не выбранная семья (`resolveMeasuredKind`); лист в клетку, добавленный при выбранной
  линейке, уходит к клетке. Перемер по новому контуру у чистого листа разлиновку не ищет, но подтягивает каждое
  поле до фолбэка от нового контура (`rebuildBlankRuling` в `SheetMarkupEditor/OutlineTool/`): ручное поле,
  оказавшееся снаружи нового листа, сдвигается внутрь, иначе текст начался бы за краем бумаги. Клемп живёт у
  перемера контура, а не в сборке разлиновки: ту зовут импорт, чтение JSON, перечтение хранилища и ручная
  правка — там он двигал бы ручные поля при каждом чтении.

## Офлайн и установка

После первого визита приложение открывается и работает без сети — вкладкой и установленным окном. Делает это
`vite-plugin-pwa` в режиме `generateSW`: он кладёт в `dist` `manifest.webmanifest` и `sw.js`, а Workbox складывает в
precache весь собранный проект. Настройки — в `vite.config.ts`, одним блоком `VitePWA`.

**Состав precache.** `workbox.globPatterns` — `**/*.{js,css,html,json,svg,png,jpg,ttf,webmanifest}`, то есть весь
`dist`: код и разметка, все восемь листов пресет-пака с картами текстуры, `paper/profiles.json`, все `.ttf`, обе
сцены, иконки и сам манифест. Список задан явно, потому что дефолт Workbox (`js,css,html,ico,png,svg`) молча выронил
бы `.jpg`, `.ttf` и `profiles.json` — ровно то, без чего оффлайн-генератор превращается в пустой лист. Вне precache
остаются три вещи: `sw.js`, его workbox-рантайм и `404.html`. Последний создаёт workflow деплоя копией `index.html`
уже после `vite build`, и это правильно: он нужен ровно для первого захода на маршрут SPA, пока service worker не
установлен, а дальше навигации обслуживает `navigateFallback`. Порог `maximumFileSizeToCacheInBytes` — 2 МиБ,
объявлен константой в `vite.config.ts`, и тест полноты читает его оттуда, а не держит свою копию числа.

Добавили лист, шрифт или файл с новым расширением — список расширений обязан это покрыть; сторожит его
`npm run test:pwa` (`tests/pwa-precache.test.ts`), а не глаз.

**Базовый путь.** Адреса precache делает абсолютными от базы `workbox.modifyURLPrefix: {'': basePath}`; в
`navigateFallback` база подставляется вручную — `modifyURLPrefix` до него не достаёт. Иконки манифеста плагин в
precache не добавляет (`includeManifestIcons: false`): он ищет их по `src` без базы и при `BASE_PATH=/autograph/` не
находит, а при пустой базе кладёт вторыми экземплярами поверх `globPatterns` — который берёт их при любой базе.
Единственный относительный адрес в списке — `manifest.webmanifest`: плагин кладёт его через
`additionalManifestEntries`, а те применяются после `modifyURLPrefix`. Резолв от `<base>sw.js` верный, поэтому тест
полноты сверяет адреса **после резолва**, а не по префиксу.

**Регистрация и плашка.** `src/app/model/serviceWorkerRegistration.ts` — единственный файл с импортом
`virtual:pwa-register`: этот модуль создаёт плагин сборки, и ни vitest, ни Storybook его не резолвят. Он остался
рядом с точкой входа, а не уехал в слайс плашки: попади он в её публичное API, виртуальный импорт тянулся бы в
каждый тест, который рисует `App`. Всё остальное приложение получает регистрацию аргументом. Обе оговорки — один
файл с виртуальным импортом и вызов регистрации только под `PROD` — сторожит `tests/service-worker-state.test.ts`
обходом `src/`, а не договорённостью.

Состояние живёт вне React — модульный стор `startServiceWorkerRegistration` + `useServiceWorkerState` в
`widgets/ServiceWorkerBanner/model/`: регистрация начинается в `main.tsx` до первого рендера, чтобы кэш пошёл
качаться сразу, а не с монтажа плашки. Хук отдаёт `{isOfflineReady, hasUpdate, update, dismiss}`.

Плашка (`widgets/ServiceWorkerBanner/ui/`) рисуется в `App.tsx` рядом с маршрутами, а не в шапке: `AppHeader` — общий
виджет трёх экранов, и состояние service worker связало бы её с инфраструктурой приложения. Блок фиксирован по левой
колонке текста и в область просмотра листа не заходит; обёртка условная — пустой фиксированный блок перехватывал бы
клики по колонке. Плашка одна на оба сообщения, потому что `dismiss` гасит оба флага разом: сообщение о готовности
само гаснет через 6 с, появившееся обновление снимает таймер и перебивает его.

`registerType: 'prompt'`, а не `autoUpdate`: тихая перезагрузка пришлась бы посреди набора текста, а каретку и
прокрутку листа сессия в `localStorage` не переживает. Новая версия проверяется `registration.update()` по часовому
таймеру, на `visibilitychange` при возврате во вкладку и на `focus` окна — генератор живёт одной вкладкой часами, и без
своей проверки предложение обновиться дошло бы только после перезагрузки. Слушателя два, потому что у установленного
приложения вкладок нет: там о возврате сообщает только `focus`. `updateViaCache: 'none'` при этом **не задаётся**: у
`registerSW` такого параметра нет, и выставить его можно лишь своей регистрацией в обход плагина. Роль «HTTP-кэш не
отдаёт старый `sw.js`» закрыта этими же двумя проверками.

**Разработка идёт без service worker.** `devOptions.enabled: false` (значение по умолчанию, записанное явно) — dev-сервер,
Storybook и тесты работают без него, иначе правки не доходили бы до экрана без ручной очистки кэша. Вдобавок
`injectRegister: null`, а вызов `startServiceWorkerRegistration` в `main.tsx` стоит под `import.meta.env.PROD`: скрипт
от плагина зарегистрировал бы service worker и в статическом Storybook, который собирается тем же production-билдом
Vite. Проверка — DevTools → Application: на `npm run dev` и `npm run storybook` там пусто.

**Аварийная разрегистрация.** Ошибочный релиз не убирается снятием `sw.js` с раздачи: установленный service worker
продолжит жить у пользователей и отдавать им старый кэш. Выход — публикация версии, где `VitePWA` в `vite.config.ts`
отключён, а в `main.tsx` вместо регистрации идёт
`navigator.serviceWorker.getRegistrations().then((registrations) => registrations.forEach((registration) => registration.unregister()))`.
Она разберёт установленное у тех, кто зайдёт. В штатном же обновлении старые кэши подчищает
`cleanupOutdatedCaches: true`, а `localStorage` (сессия) и IndexedDB (свои листы) смена версии не трогает.

Тесты лежат плоско в `tests/`, хелперы — в `tests/helpers/` (генераторы синтетических листов, контексты-записыватели
вызовов canvas, растеризатор чернил, модель строчного бокса). Компонентные тесты просят jsdom директивой
`@vitest-environment jsdom` в шапке файла; заглушки того, чего в jsdom нет (`ResizeObserver`, `document.fonts`,
`FontFace`, `Range.getClientRects`, canvas), — в `tests/helpers/jsdom-setup.ts`. Там же IndexedDB из `fake-indexeddb`
(только `devDependencies`) и обёртка `structuredClone`, которая сохраняет `Blob`: родной из Node превращает файл
в пустой объект, и запись листа в тестах теряла бы фотографию. Воркера в jsdom нет — разбор снимка там идёт в
основном потоке тем же путём.

Тест полноты precache вынесен в отдельный проект vitest (`pwa`, `tests/pwa-precache.test.ts` + сборщик
`tests/helpers/pwa-build.ts`) и в `npm test` не входит: он собирает проект трижды — базы `/` и `/autograph/` плюс
проба на порог размера, — и в проекте `unit` делал бы минутным каждый коммит, потому что гейт коммита гоняет
`vitest --changed`. Собирает он сам, в `node_modules/.cache/pwa-precache/<база>`, а не читает готовый `dist`:
чтение «если есть» было бы вечно зелёным, и `dist` разработчика заодно не затирается. В сборке принудительно
`NODE_ENV=production` — под vitest он `test`, и сверялся бы отладочный `sw.js`.

Проверки, которые нельзя подменить скриншотом: связность почерка считается числом связных областей чернил в растре
(эталон к разрыву слеп), совпадение прогонов — лентой вызовов контекста **после** рендерера (сравнение входных
параметров не поймало бы случайность внутри отрисовки), попадание на разлиновку — арифметикой по модели строчного
бокса, а не глазами.

Эталоны скриншотов снимаются только в docker-образе Playwright: рукописные шрифты растрируются в macOS и Linux
по-разному. Прогон вне образа не предусмотрен — обе команды (`test:visual`, `test:visual:update`) идут через
`visual:docker`. Seed прогона в stories фиксирован — иначе каждый прогон давал бы другой почерк. Подробности —
`tests/visual/README.md`.

## Линтинг

```
eslint.config.mjs        # flat config: typescript-eslint + prettier + jsdoc + simple-import-sort + unicorn +
                         # react-hooks и jsx-a11y на **/*.tsx
stylelint.config.mjs     # stylelint-config-standard + послабления под Tailwind 4
steiger.config.ts        # границы слоёв FSD
.lintstagedrc.mjs        # eslint --fix / stylelint --fix / prettier --write по staged-файлам
.husky/pre-commit        # lint-staged + tsc + vitest --changed параллельно
```

Осознанные послабления:

- `no-undef` выключен для TS: необъявленное имя ловит `tsc`.
- В stylelint выключены `property-no-vendor-prefix` / `value-no-vendor-prefix`, `import-notation` и разрешены
  at-правила Tailwind (`@theme`, `@apply`, `@layer`, …): Tailwind 4 объявляет тему прямо в CSS, а
  `@import 'tailwindcss'` плагин ищет по строковой форме.
- `allowImportingTsExtensions` включён в `tsconfig.json`: Storybook предупреждает о локальных импортах без расширения
  в `.storybook/main.ts` и просит писать их с `.ts`, а без флага такой импорт не пропускает `tsc`. Проверка типов от
  этого не слабеет — сборка и так идёт через `noEmit`, а расширение стоит ровно в одном импорте.

`.claude/hooks/lint.sh` — PostToolUse-хук: после каждой правки гоняет по файлу eslint (+`tsc --noEmit` для `.ts`/
`.tsx`) или stylelint + `prettier --check` для `.css`. Ошибки в правленом файле блокируют правку.

## Воркфлоу задачи

Одна задача — один issue, одна ветка, один PR. Репозиторий на GitHub, поэтому CLI — `gh` (`glab` здесь не
применяется). Номер issue — сквозной идентификатор: он в имени ветки, в теле PR и в коммитах.

1. **Issue.** Задача заводится в репозитории до правок — чтобы у PR был предмет, с которым аудит сверяет результат.
   Тело описывает наблюдаемое поведение и критерий готовности, а не план правок.

   ```bash
   gh issue create --title '<кратко, что должно измениться>' --label enhancement --body '<описание и критерий готовности>'
   ```

   Метки из набора репозитория: `bug`, `enhancement`, `documentation`, `accessibility`.
2. **Ветка от master.** Только от свежего `master`, не от текущей ветки: иначе в PR приедут чужие коммиты.
   Имя — `<type>/<номер issue>-<краткое-имя>`, где `type` — `feature`, `fix`, `chore`, `docs`.

   ```bash
   git switch master && git pull --ff-only
   git switch -c feature/42-sheet-perspective
   ```
3. **Правки и PR.** Правки идут в этой ветке; перед PR — `npm run lint` и `npm test` (гейт коммита их не заменяет:
   `.husky/pre-commit` гоняет vitest только по изменённым файлам). PR привязывается к issue ключевым словом в теле,
   иначе issue придётся закрывать руками.

   **Каждый PR поднимает версию** в `package.json` (`npm version <версия> --no-git-tag-version` — заодно правит
   `package-lock.json`): обычный PR — минор, глобальное изменение (переделка продукта, несовместимая смена формата
   сессии или своих листов) — мажор с обнулением минора. Третье число руками не трогается: версия в шапке —
   `<мажор>.<минор>.<число коммитов>`, его подставляет сборка (`readAppVersion` в `vite.config.ts`). Мажор
   нулевой, пока основной функционал не доделан, и шапка рисует после номера пометку `beta`; выход из беты — это
   мажор `1` и снятие пометки в `AppHeader` одним PR.

   ```bash
   git push -u origin HEAD
   gh pr create --base master --fill --body 'Closes #42

   <что сделано и почему так>'
   ```
4. **Аудит.** Пользовательский скилл `review-staged` (`~/.claude/skills/`, не в репозитории) в режиме «ветка
   против master». Без него аудит идёт вручную по тому же диффу и тем же `.claude/rules/*.md`, с тем же
   требованием к находке: файл, строка, цитата из файла.

   Находки ложатся **inline-комментами в PR** — привязанными к файлу и строке, а не одним общим комментом:
   резолвить на повторном аудите можно только тред, заведённый на строке.

   Тело ревью лежит в файле (`/tmp/review.json`), а не в флагах: у `gh api` нет формы для массива объектов.

   ```json
   {
     "commit_id": "<sha головы ветки>",
     "event": "COMMENT",
     "comments": [
       {"path": "src/pages/Generator/lib/paper/detectRulingBend.ts", "line": 118, "side": "RIGHT", "body": "<находка и что с ней делать>"}
     ]
   }
   ```

   ```bash
   gh api --method POST repos/Corvus278/autograph/pulls/<N>/reviews --input /tmp/review.json
   ```

   Один тред — одна находка. `event: COMMENT`, а не `REQUEST_CHANGES`: автор PR и ревьюер здесь одно лицо, и
   GitHub не даёт запросить правки у самого себя.

   `line` берётся только из строк, попавших в дифф PR, — на остальные GitHub отвечает 422. Находка в строке,
   которой дифф не касался (у `review-staged` это `pre_existing`), идёт комментом к файлу целиком
   (`"subject_type": "file"` вместо `line` и `side`) либо в общий тред PR (`gh pr comment`). Общий тред резолву
   на шаге 6 не поддаётся — его закрывает ответ автора.
5. **Правка комментов.** Каждая находка правится отдельно и пушится в ту же ветку. Спорную не правят молча —
   ответ в треде с обоснованием тоже закрывает находку.

   ```bash
   gh api --method POST repos/Corvus278/autograph/pulls/<N>/comments/<databaseId первого коммента треда>/replies -f body='<как поправлено или почему нет>'
   ```

   Ответ идёт на **комментарий**, а не на тред: у REST есть только `databaseId` первого коммента, а резолв (шаг 6)
   просит `id` треда из GraphQL. Оба берутся одним запросом ниже.
6. **Повторный аудит и резолв.** Тот же `review-staged` по обновлённой ветке. Резолвится только тред, правка
   которого подтверждена в коде: «ответил» и «поправил» — разные вещи. Резолв идёт через GraphQL — у REST такой
   операции нет.

   ```bash
   # нерезолвнутые треды с путями и строками
   gh api graphql -f query='query($owner:String!,$repo:String!,$pr:Int!){repository(owner:$owner,name:$repo){pullRequest(number:$pr){reviewThreads(first:100){nodes{id isResolved path line comments(first:1){nodes{databaseId body}}}}}}}' \
     -F owner=Corvus278 -F repo=autograph -F pr=<N> --jq '.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved | not) | {id, path, line, commentId: .comments.nodes[0].databaseId}'

   gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -F id=<id треда>
   ```

   Находки, всплывшие на повторном аудите заново, — новые треды: шаги 5 и 6 повторяются, пока нерезолвнутых не
   останется. Мерж — после этого: squash, чтобы в `master` от задачи остался один коммит, и с удалением ветки —
   issue закроется сама по `Closes` из тела PR.

   ```bash
   gh pr merge <N> --squash --delete-branch
   ```
